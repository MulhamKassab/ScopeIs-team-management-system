ScopeIs · 6 October 2026

Clearer user journeys across every tab

Task: simplify the entire existing application without losing its working features. Fresh live screenshots cover all 20 Super Admin tabs. The implementation then refines navigation, task priority, search and progressive disclosure, with separate role guidance.

Canonical user stories and acceptance boundaries · Application

What was already working

The monthly timetable offers Month, People and Agenda; map selection shows who, where and when; team membership and client records have concrete controls. Leave review, private files and role-specific permissions provide a useful foundation. These flows are retained.

What changed

Home prioritizes decisions and the published plan. Skills uses one selected person. Find cover gains person/work search and day groups. Conversations are compact, dated and contextual; technical activity references are expandable. Familiar labels and short, optional guidance connect every tab to its next step.

Numbered walkthrough and fresh evidence

1. Home Working, too much secondary information

Observed: Review queues are useful. Nine large counts compete with the primary work task; lower tables expose technical team references and record IDs.

Implemented: Check waiting decisions or your next work → open Timetable. Additional figures are under More team insights.

2. Timetable Clear overview, editing path needs explanation

Observed: Month, People and Agenda are discoverable. Published versus unpublished is visible; Plan work does not explain client schedule selection or the next approval step.

Implemented: Choose month and view → open a day. Managers select a client plan, prepare Draft work and propose; only Super Admin publishes.

3. Find cover Working, hard to scan a whole month

Observed: Who/where/what is readable, but all 18 work cards form a long unfiltered list. The handoff to Replacements uses a different word from coverage.

Implemented: Search work or choose a person → open a day → Check cover → replace someone or add extra support → follow Cover requests.

4. Cover requests Decision is understandable; conversations dominate

Observed: Request cards explain replacement versus extra support. Every conversation is fully open below; the distinction between decisions and participant requests is unclear.

Implemented: Super Admin reviews the decision queue; Admin follows their own requests. Approval prepares a Draft; publication remains a separate Timetable action.

5. My requests Working, request identity is unclear

Observed: The navigation promises assignments but page shows request discussions. Generic type/status headings omit person, date and place; messages and policy copy appear before a compact request overview.

Implemented: Read request type, date and status → expand conversation → exchange messages. Managers see work context only after current-role and scope checks.

6. Leave Clear review queue

Observed: Pending requests and Review are clear. Dates use raw database formatting; page terminology can become Leave requests while allowance settings remain secondary.

Implemented: Employee/Admin checks balance, chooses dates and follows status. Super Admin reviews dates, balance and work conflicts; Admin team view shows approved leave only.

7. Work map Useful map, technical labels remain

Observed: Selected person, time and place are clear with direct actions. Coverage gaps and Approved unavailable labels need everyday wording; technical planning explanations can be secondary.

Implemented: Choose date → search a person or choose a pin/site → read time and place → check cover or open Timetable.

8. People Readable directory; labels and priority need refinement

Observed: Search and row actions work. Long navigation label and internal terms such as Designation/visible people add friction; job titles would help identify each person more than prominent employee codes.

Implemented: Search/filter → open person → review work details, recorded skills and permitted documents. Team/job title and system role/access stay separate.

9. Teams Clear membership controls

Observed: Create, Rename, Add member and Remove are concrete. Keep these controls and add brief workflow help rather than more introductory copy.

Implemented: New team → Add member → Rename or Remove membership. Each person has one team; access grants remain separately managed.

10. Job titles Working, unfamiliar terminology

Observed: Membership is concrete. Job titles is a more familiar name for this catalogue; avoid repeated long empty-member wording.

Implemented: New job title → Add member → manage membership. Designation is the same underlying catalogue; a job title never grants system permissions.

11. Skills Working, two competing employee selectors

Observed: Selecting someone to review is separate from selecting someone to record a skill. The catalogue, technical warnings and archive controls occupy the main screen; a single selected-person path would be clearer.

Implemented: Super Admin chooses one person → View skills → Record skill for that person. Manage skill list is a secondary disclosure. Admin searches skill holders; Employee reads own skills.

12. My profile Working, document terminology and contrast need attention

Observed: Work facts and Edit profile are clear. Capability evidence is unfamiliar wording; blue Add buttons have visibly muted text. Team name is a raw reference suffix rather than the managed name.

Implemented: Edit profile → add documents/experience → follow review states. The managed team name is displayed; Add button text is readable.

13. Clients Clear records and actions

Observed: Create, search and Open client are clear. Explain the setup order Client → Project → Location → Timetable in optional help, preserving the existing record navigation.

Implemented: Search/create client → add projects and same-client sites → plan people in Timetable.

14. Projects Clear cards, handoff needs guidance

Observed: Client name, status and dates give good context. Clarify that a project describes the work, a location describes where, and staffing is assigned in Timetable.

Implemented: Choose client → prepare project, dates, sites and requirements → assign people in Timetable.

15. Locations Clear worksite records

Observed: Site and client names are clear. Optional workflow help should explain linking a same-client project before assigning work; no new location or tracking behavior is needed.

Implemented: Choose client/site → record address and visit instructions → link a same-client project → use the site in Timetable.

16. Reports Working, jargon and long catalogue

Observed: Reports are grouped by goal, but Published allocation, client-month and lifecycle require domain knowledge. Add task search and familiar titles while retaining clear Published/planning distinctions.

Implemented: Search by topic → open familiar report title → filter dates and scope → read/download where permitted. Unpublished plans remain explicitly separate.

17. Notifications Working, updates lack a concrete action label

Observed: Unread and archive controls are clear. Repeated Open related record and capability evidence wording obscure the task; use action labels based on the existing authorized destination.

Implemented: Inbox/Unread → open the authorized request, conversation, document or timetable → mark read or archive independently.

18. Accounts Working, dense administration terms

Observed: Search and Reset password are discoverable. Account administration, Credentials, raw role constants and credential-history density can be simplified without changing identity or permission behavior.

Implemented: Search person → check Sign-in setup and readable system role → create/enable sign-in or reset password through existing controls.

19. Activity log Working, technical details dominate

Observed: Action, person and time are visible. Raw constants, UUIDs and metadata overwhelm the event list; move them into Record details and use friendly role/record-type labels.

Implemented: Filter action, record type, person/date → read event → expand Record details only when references or safe metadata are needed.

20. Settings Honest placeholder, secondary only

Observed: Settings clearly says unavailable. Keep it marked Coming soon and do not invent unconfirmed configuration features.

Implemented: Clearly marked Coming soon. Guidance points to the working Profile, Accounts and people tools; no unconfirmed settings are implemented.

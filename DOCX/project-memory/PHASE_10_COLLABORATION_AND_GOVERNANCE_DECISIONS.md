# Phase 10 — Collaboration and Governance Decisions

Phase ID: `SCOPEIS_PHASE_10_NOTES_DISCUSSIONS_NOTIFICATION_CENTRE_AND_AUDIT_INTERFACE_R1`

This file records the decisions applied while implementing the Phase 10 collaboration-and-governance journey. It supplements, and does not replace, [`PRODUCT_REQUIREMENTS.md`](PRODUCT_REQUIREMENTS.md), [`ROLE_AND_PERMISSION_MODEL.md`](ROLE_AND_PERMISSION_MODEL.md), and [`DECISIONS_AND_CONSTRAINTS.md`](DECISIONS_AND_CONSTRAINTS.md).

## Confirmed by the product owner

1. **Shared Client, Project, and Location notes are manager-scoped, not universally shared.** "Shared" means shared with every authenticated user already authorized on the parent record: Super Admin globally, and Admin only where their Client, Project, or Location scope authorizes that parent. Employees hold no Client, Project, Location, or shared-note access. This replaces the earlier ambiguous "all authenticated users" reading of NTE-005 and must not be used to widen Employee permissions.

## Decided during implementation

2. **Shared-note lifecycle.** Plain text only, maximum 5,000 characters, no HTML or attachments. Creation and reading require parent authorization; editing is author-only; archive is Super Admin-only and requires a reason. Every edit writes the superseded content to `operational_note_revisions` in the same transaction, so an edit is never lossy and nothing is hard-deleted. Shared-note activity creates no Phase 10 notification.
3. **Employee-management note lifecycle.** Visibility (`private_to_author` or `shared_upward`) is fixed at creation and cannot change. Content is immutable; corrections archive the old note and create another. A private note remains readable only by its author, including from another Super Admin. A shared-upward note is readable by its author and by an authorized Super Admin whose current scope still covers the subject. Access always uses the reader's current role and scope; the stored author role is historical context only, and an author who is later demoted retains access to what they wrote. The subject, an Employee actor, a peer Admin, an out-of-scope Admin, and a guessed id all receive one non-enumerating refusal. No Phase 10 notification is generated.
4. **Discussions are limited to replacement requests.** `replacement_request` is the only supported parent; any other parent type fails closed at both the validation boundary and a database check constraint. Participants are derived live from the request (requester plus the currently named employee(s)); role never confers participation. Messages are plain-text, append-only, immutable, ordered by `(created_at, id)`, and archivable only by their own author. No attachments, HTML, edits, mentions, or reactions.
5. **Notification centre contract.** Every notification belongs to exactly one recipient. The inbox is newest-first, paginated at 25 with stable `(created_at, id)` ordering, and offers read, unread, archive, restore, and mark-all-read. Read state and archive state are independent and both operations are idempotent. Rows store no private display content: titles and summaries are derived from the event type, and a related-record link is reauthorized server-side for the current recipient, yielding a neutral unavailable state for an inaccessible or unknown target.
6. **Audit-history contract.** `/audit` is Super Admin-only, read-only, newest-first, paginated at 50, and filterable by action, target type, actor, and a bounded date range. Rendering uses a per-action allowlist of safe identifiers, enumerable state, counts, and booleans; raw JSON metadata is never rendered and an unknown action receives a generic label with no metadata. Viewing the page generates no audit event, and the interface supports no mutation, deletion, or export. Admin and Employee receive a non-enumerating refusal.
7. **Phase 9 evidence-integrity correction.** When an owner materially changes verified or reviewed evidence — title, issuer, issue date, expiry date, related skill, details, file attachment, or file replacement — the item resets to `unreviewed` and its review and verification provenance is cleared in the same transaction, with an `evidence.review_reset` audit event carrying safe metadata only. Review actions never reset state and never modify `last_submitted_at`. Phase 7 coverage and replacement eligibility remain unchanged.

## Deliberately deferred

8. **Coverage linkage for verified evidence (Phase 9 sub-phase 9.9).** Whether verification affects coverage or replacement eligibility remains an unapproved product decision. Phase 9 records and exposes verification state; Phase 10 preserves that lifecycle without letting it change Phase 7 results.
9. **Notification and discussion expansion.** Email, SMS, push, WebSocket or other real-time delivery, external queues, notification retention or purge automation, assignment discussions, and Ticket discussions remain out of scope. Phase 11 owns dashboards, reports, and exports; Phase 12 owns Ticket System integration.
10. **Audit export and mutation.** No export, no deletion, and no editing of audit history is implemented or planned for Phase 10.
